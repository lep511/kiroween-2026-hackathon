# Rolling 30-day accumulation of the Insurgency Report (v1)

The daily report no longer holds only the day's news. Every run, local CLI and Step Functions alike, starts from the last published `snapshot.json`. It drops articles whose URL is already stored before any agent call, adds the day's new strikes, expires strikes published more than 30 days before the report date, renumbers ids `1..N`, and always publishes. A day with zero articles publishes the accumulated set. A batch with more than 20% discards publishes the accumulated set without its new strikes, and the Timeline records the day as `rejected`; a conditional put keeps a rejected rerun from replacing a `published` row. The change also packages the Lambdas from a dedicated `infra/.build/lambda`, narrows the CloudFront bucket policy to the site files plus `snapshots/*`, logs every title the deterministic filter drops, and recreates `docs/report-ingestion-news.md` byte-for-byte from the source (verified with `cmp`). All 222 tests pass, ruff and black are clean, and the three `snapshot.bin` copies share md5 `026f1091…`.

Watch for: the prefix-conditioned `s3:ListBucket` grant probably does not turn a missing `snapshots/latest/snapshot.json` into `NoSuchKey`, so the first cloud run would fail in Fetch with `AccessDenied` (likely). Skipped non-incidents are not remembered and go back to the agent every day they stay in a feed (confirmed). Nothing stops a run with an older `report_date` from overwriting `snapshots/latest/` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The accumulation logic sits in `transform.py`, and both entry points share it. `drop_known` filters before extraction, but fully curated rows are rebuilt on every run, and that skews the counters `assemble` reports in offline mode. Neither the CLI nor Assemble checks that the new report date is not older than the previous one before overwriting the latest snapshot.

The S3 read path depends on IAM semantics that the tests cannot check. `get_optional` turns `NoSuchKey`/`404` into "first run", and anything else propagates. The template's `s3:ListBucket` grant is conditioned on `s3:prefix`, and a `GetObject` request most likely does not carry that key in its context. The template test pins that exact statement, so the test reinforces the gap.

URL dedupe covers only strikes stored in the previous report. Skipped non-incidents, discarded articles, and every article of a rejected batch go back to the agent on the next run. That is by design for discards and rejections, but for non-incidents it means paying for the same verdict every day.

1. **Prefix-scoped ListBucket likely yields AccessDenied on the first run** — Fetch and Assemble probably get 403 instead of `NoSuchKey` when `snapshots/latest/snapshot.json` does not exist, so the first cloud run fails before any report exists. Drop the `s3:prefix` condition (or verify on a real bucket) and update `test_statemachine.py`.
2. **Non-incident verdicts are not remembered** — an item the agent skips is re-extracted on every run while it stays in the feed. Consider persisting skipped URLs (for example in the snapshot or the Timeline), or accept and document the cost.
3. **No guard against a report date older than the latest snapshot** — a backfill or manual execution with an earlier `report_date` overwrites `snapshots/latest/` (and, locally, `--out`) with an older-dated report that still keeps newer strikes. Write `latest/` only when `report_date >= previous.report_date`, or reject the run. Overlapping executions have a related problem: the later Assemble drops the other execution's new strikes. Accept that for a daily cron or document it.
4. **Curated rebuilds inflate `new` and dilute the discard ratio** — in offline mode every in-window curated row counts as new and fetched on every run, so the Timeline's `new`/`carried` are misleading and failures are diluted by rows that cannot fail. Exclude rebuilt-known rows from `fetched`/`new`, or document the behavior.

### First-run read of `snapshots/latest/` under the prefix-conditioned ListBucket

Fetch and Assemble both call `_load_latest` (`pipeline/stages.py:252-259`), which relies on `S3Storage.get_optional` to map a missing key to `None`. S3 returns `NoSuchKey` for a missing object only when the caller holds `s3:ListBucket` on the bucket. Otherwise it returns `AccessDenied`, and `get_optional` re-raises that by design. The grant in `infra/template.yaml:124-130` (Fetch) and `:186-192` (Assemble) reads:

```yaml
- Effect: Allow
  Action: s3:ListBucket
  Resource: !GetAtt SnapshotBucket.Arn
  Condition:
    StringLike:
      s3:prefix: "snapshots/latest/*"
```

`s3:prefix` is a request parameter of `ListObjects`. The implicit ListBucket check behind a `GetObject` most likely runs without it, and a `StringLike` condition on an absent key evaluates to false. If so, the grant never applies on the GetObject path. On a fresh stack, Fetch then raises on its first execution, the Lambda-only Retry does not cover it, and the state machine fails every day until someone seeds `snapshots/latest/snapshot.json` by hand (likely). `pipeline/tests/test_statemachine.py:205-211` asserts this exact statement, so the suite cannot catch the problem. The simplest fix is an unconditioned `s3:ListBucket` on the bucket for these two functions. It only exposes key names, and those are not sensitive here. Confirm with `aws s3api get-object` on a missing key under the function role after deploy. `StringLikeIfExists` is not a good substitute because it also allows listing the whole bucket. The steering doc, `design.md`, and `tasks.md` all describe the grant as "prefix-scoped" and would need the same correction.

### What the URL dedupe does not remember

`drop_known` (`pipeline/transform.py:91-120`) builds its known set from the previous report's strike URLs only (`stages.fetch` passes `latest.strikes`, and `build_report` does the same at `transform.py:238`). An article the agent answers `is_incident: false` for is skipped and appears nowhere in the published report. On the next run it passes the deterministic filter again and gets a fresh Opus call that reaches the same verdict, for as long as the feed keeps the item. BBC and NYT feeds often keep items for several days (confirmed from the code path; the cost depends on feed retention). Re-extracting discards and rejected batches gives them another chance. Re-running a non-incident cannot change the outcome.

### Report date ordering between runs

Neither `stages.assemble` nor the CLI compares the new `report_date` with `previous.report_date`. Assemble always writes `LATEST_JSON_KEY` and `snapshots/latest/snapshot.bin` (`pipeline/stages.py:399-402`). A manual execution with an older `report_date`, which `preflight` accepts from the event, makes `latest/` go back in date. Because `within_window` keeps future-dated strikes, that older report still holds the newer strikes (confirmed). The same happens locally when `--date` is earlier than the date of the `snapshot.json` in `--out`. A related, rarer case: if two executions overlap (the schedule plus a manual start), the later Assemble wins, and the strikes the other execution added disappear until a later run re-extracts them from the feed (likely, only with concurrent executions). A guard that refuses to move `latest/` backwards in date would cover the first case cheaply. The second case may be acceptable for a daily cron.

### Curated rebuilds and the counters

A fully curated row whose URL is already stored passes `drop_known` and goes through `assemble` as a fresh strike that replaces its carried copy. In offline mode (CLI `--offline`, or `OFFLINE=1` in the cloud), every in-window curated row counts toward `fetched` and `new` on every run, so the CLI summary and the Timeline row show `carried: 0` and `new: 5` on a day with nothing new (confirmed). These rows cannot fail, so they also lower the discard ratio for any partial curated row that does go to the agent. Rebuilt rows also get a new id, and the jitter seed in `build_strike` includes the id, so their markers move slightly between runs. This mainly affects the demo and is not a correctness problem for live runs, but the counters do not match what the Timeline appears to say.

### Test coverage

The tests cover the accumulation paths in both entry points, including exit codes 2/3/4 and the conditional Timeline put. Not tested: two consecutive CLI runs on different dates where a strike crosses the 30-day boundary between them; a previous report dated after the current report date; and IAM behavior for the missing-key read, which the unit tests cannot cover and which `sam validate` or a live run would need to confirm.
